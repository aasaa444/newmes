## 2. 可信度分级

| 级别 | 进入条件 | 可对外表述 |
|---|---|---|
| 未验证 | 仅有想法或文档 | 设计中/待验证 |
| 已实现 | 代码或配置存在 | 已实现，尚未完成验证 |
| 技术验证通过 | 自动化、浏览器、SQL Server、部署和证据门禁通过 | 候选系统完成技术验证 |
| 制造从业者评审通过 | 工艺、质量、计划等专业人员审阅并记录意见 | 已完成行业/专业评审 |
| 真实现场验证通过 | 真实工厂、真实数据和实际班次验证并签字 | 已完成现场试点验证 |

在没有真实评审和试点前，项目不得使用“已落地”“已上线”“已验收”等表述。

## 3. 测试层级

| 层级 | 目的 | 典型内容 |
|---|---|---|
| 领域单元测试 | 快速验证状态机和不变量 | 生命周期、完成门禁、质量处置、余额规则 |
| API/应用集成测试 | 验证授权、命令、错误和事务边界 | 角色拒绝、幂等请求、回滚、审计 |
| SQL Server 集成测试 | 验证真实数据库语义 | Migration、约束、并发、Inbox/Outbox |
| 契约测试 | 验证适配器和消息格式 | 版本、必填、幂等键、错误响应、回执 |
| 浏览器 E2E | 验证真实用户工作流 | 计划端、工位端、质量端、谱系查询 |
| 部署与恢复测试 | 验证可安装、可升级、可恢复 | Compose、HTTPS、健康、备份恢复、冒烟 |
| UAT | 由关键用户确认业务可用性 | 正常、返工、报废、集成异常和查询 |

## 4. 四条强制端到端场景

### 4.1 E2E-01 正常完工与单件谱系

前置：产品、BOM、路线、追溯策略、测试规范、身份来源和物料已准备；ERP 发送订单。

步骤：订单入站 -> 下达冻结快照 -> 物料交接/发料 -> START_WIP -> 关键件 SN 和 Lot 耗用 -> 固件配置 -> 逐项功能测试通过 -> 终检 -> 合格完工 -> 仓储接收 -> ERP 回执 -> 关闭 -> 按 SN 导出谱系。

验收：谱系内容完整；模板后续修改不改变该 SN 快照；制造完工、仓储接收和 ERP 入账时间可区分。

### 4.2 E2E-02 测试失败、返工与复测

步骤：功能测试至少一项失败 -> 保存全部测量 -> 创建不合格和质量保留 -> 质量工程师决定返工 -> 执行返工作业 -> 复测通过 -> 授权解除保留 -> 完成后续工序。

验收：原失败测试不可编辑；返工和复测关联清晰；未解除保留前完工被拒绝；操作工无处置审批权限。

### 4.3 E2E-03 报废与订单数量平衡

步骤：在制 SN 发现严重不合格 -> 质量工程师报废 -> 物料按规则冲正/保留责任 -> 订单有在制时尝试取消 -> 系统拒绝 -> 处理剩余 SN -> 受控短结或执行完成。

验收：报废事实和依据可查；订单取消限制有效；计划数、投产数、完工数、报废数和未投产数平衡。

### 4.4 E2E-04 集成重复、失败、重试与对账

步骤：重复提交同一订单消息 -> 只创建一次 -> 制造完工生成 Outbox -> 模拟 ERP 暂时失败 -> 消息进入 Failed 并记录错误 -> 自动/人工重试 -> 对方幂等接收 -> 回执 -> 对账关闭。

验收：无重复订单和重复入账；失败不标记成功；每次尝试和最终回执可查；订单在对账前不能关闭。

## 5. 关键负向测试

- 未下达订单 START_WIP 必须失败。
- 当前工序与工位不一致的跳站必须失败。
- 示例密钥、开放 CORS 或 `sa` 在生产配置中必须触发门禁失败。
- 已投产订单取消必须失败，暂停后新投产和正常过站必须失败。
- 未发料/未授权负库存、同一部件 SN 重复绑定必须失败。
- 必测项目缺失、测量越界或未决质量保留时完工必须失败。
- 操作工批准处置、系统管理员绕过业务审批必须失败。
- 重复 Inbox、重复回执和并发 Outbox 认领不得产生重复业务结果。
- 旧数据库升级失败必须停止发布，不能自动删库重建。

## 6. 测试数据策略

演示和测试数据必须明确标记为非生产。固定数据集至少包含：一个正常订单、一个返工订单、一个报废/短结订单和一个集成故障订单；每个场景使用稳定且不同的成品 SN、关键件 SN、Lot 和消息 ID。测试结束后可重复重建，生产环境禁止装载。

旧演示数据仅作为升级夹具和行为回归。无法由原记录证明的固件、测量、Lot 或处置信息不得通过迁移补造。

## 7. 需求追踪与证据包

每条 Must 需求至少关联一个测试或人工验收步骤。每个版本证据包包含：

1. 版本、提交、构建环境和执行时间。
2. 需求追踪矩阵及未覆盖说明。
3. 单元/API/SQL Server/契约/浏览器测试结果。
4. 四条端到端场景的输入、关键截图和输出。
5. 固定成品 SN 的谱系 JSON/PDF 导出及校验值。
6. Migration 新装和升级结果、依赖漏洞扫描和权限拒绝证据。
7. Compose 启动、HTTPS、健康、备份恢复和冒烟结果。
8. 已知限制、未验证假设、遗留缺陷和风险接受人。

## 8. 缺陷管理

| 级别 | 定义 | 发布处理 |
|---|---|---|
| Critical | 数据丢失/伪造、越权、错误完工、重复入账、无法恢复 | 必须修复，不允许发布 |
| Major | 核心流程中断、追溯缺失、错误质量门禁 | 原则上必须修复；延期需发起人书面接受 |
| Minor | 有替代路径且不影响业务事实 | 可带入，但必须记录和计划 |
| Cosmetic | 纯视觉或文案问题 | 不阻塞技术验证，集中修复 |

## 9. UAT 组织

UAT 由计划、工艺、质量、物料、操作和 ERP/IT 的关键用户共同执行。开发人员可以协助环境和取证，但不能替代用户判定流程是否可用。每个场景记录执行人、日期、环境、数据、期望、实际、证据、缺陷和结论。

## 10. 技术验证退出标准

- 所有 Must 需求已实现并有追踪，或经正式变更移出范围。
- 四条强制 E2E 和关键负向测试通过。
- SQL Server 空库/升级、事务、幂等和并发测试通过。
- 浏览器 E2E、权限矩阵、部署、备份恢复和冒烟通过。
- Critical/Major 缺陷为零，或 Major 有明确风险接受且不损害业务事实。
- 证据包可由陌生人按说明复现，限制清单完整。

## 11. 现场验收前置条件

技术验证通过不自动进入现场验收。现场验收还需真实 SOP、物料和产品样本、扫码/测试设备、ERP 沙箱、实际账号与权限、网络、产能和班次、备份与运维责任、用户培训和签字标准。任何一项缺失都应进入 RAID，而不是隐藏在“后续优化”。

## 12. 验收签署建议

真实项目应分别签署需求/蓝图确认、UAT 结果、上线准备、试运行结果和最终验收。签署人至少包括业务负责人、计划、工艺、质量、IT 和实施方项目经理；技术负责人只能确认技术结果，不能代替业务签收。
