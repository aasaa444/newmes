# 工业路由器整机装配 MES 领域救援与可信落地规格

**Issue title:** 工业路由器整机装配 MES：领域救援与可信落地实施规格

**Status:** Ready for agent after publication

**Target label:** `ready-for-agent`

**Baseline date:** 2026-07-29

**Delivery positioning:** 单厂工业路由器整机装配 MES 试点候选系统

## Problem Statement

当前系统已经具备 ASP.NET Core、Vue、SQL Server、认证、工单、过站、质量、库存、ERP 模拟器和一批 API 集成测试，但原实现主要从演示页面和简化流程出发，尚不足以证明它是一套真实可信、可用于工厂试点设计的 MES。现有实现把部分制造概念压缩为可覆盖的状态或简单 CRUD，把 SQLite 测试、种子数据和模拟出站误当成 SQL Server 可部署性、制造事实完整性及跨系统闭环的证据。旧参考站序、角色职责、物料处理和质量放行语义也需要依据新的领域基线重新审视。

用户希望通过完全依靠 vibe coding 的方式挽救项目，同时学习 MES 业务、形成面试可讲述的项目案例，并覆盖开发、项目经理、售前工程师和企业信息化顾问等岗位。系统必须以公开行业共识和明确假设为依据，能够演示一条可重复验证的制造闭环，但不得在没有真实客户、制造从业者评审、ERP 联调和工厂试运行证据时声称已经上线、验收或真实落地。

本次工作不是重写，也不是继续扩展经营看板和空模块。核心问题是：在保留现有技术骨架的前提下，建立可信的制造执行领域内核、真实数据库演进能力、可靠集成边界、可审计单件谱系和可复现证据包，使项目最多可以诚实地达到“技术验证通过”，并为后续制造从业者评审和真实现场验证留下清晰门禁。

## Solution

以“单件全过程追溯”为首个价值闭环，将项目收敛为单厂、一条人工整机装配线的工业路由器 MES 试点候选系统。试点从已经完成上游测试的 PCBA 和其他来料进入整机装配开始，到合格成品完成制造、仓储交接、ERP 回执和生产订单关闭为止。

系统采用 ERP 计划权威、MES 执行权威的边界。ERP 或其模拟适配器通过正式入站契约提供产品、物料和生产订单；MES 在订单下达时冻结 BOM、工艺路线、追溯策略、测试规范和身份策略的执行快照，并以关系型当前状态加只追加制造事件记录实际执行。参考路线为 `START_WIP -> ASSEMBLY_BIND -> FW_CONFIG -> FUNCTION_TEST -> FINAL_INSPECTION -> COMPLETE`，可按责任配置 `PACK_HANDOFF`，但路线顺序、测试阈值、关键件粒度和返工点继续标记为待现场确认的版本化配置。

产品身份、物料事务、固件配置、测试执行、不合格、质量保留、处置、返工、复测、制造完工、仓储接收和 ERP 入账分别建模。更正以冲正、补偿或引用原事实的新事件表达，不删除或覆盖历史。入站使用幂等收件箱，出站使用事务发件箱，支持失败、重试、死信、回执和对账，不宣称严格 exactly-once。

救援按 R0 至 R6 增量推进：先冻结规格和旧行为基线；再建立 EF Core Migration、真实 SQL Server 测试及生产配置门禁；随后实现订单快照、身份、WIP、物料事务、测试质量和谱系；再完成可靠集成；最后补齐计划端、工位端、质量端和追溯端的核心工作流以及私有化部署、恢复演练和版本化证据包。现有 UI、认证和测试中仍符合新契约的部分予以复用，不符合的部分作为旧行为记录逐步替换。

## User Stories

1. As a 项目发起人, I want 系统被明确定位为试点候选而非已落地产品, so that 对外陈述与现有证据一致。
2. As a 求职者, I want 每项能力都有需求、设计、测试和证据关联, so that 我能在开发、项目管理和售前面试中讲清决策依据。
3. As a 售前工程师, I want 明确区分公开行业共识、样板假设和现场确认事实, so that 方案不会把推测包装成客户现状。
4. As a 项目经理, I want 范围、里程碑、责任人、风险、问题和验收门禁可追踪, so that 实施工作可以受控推进。
5. As a 制造从业者评审人, I want 查看仍待验证的路线、物料、测试和质量假设, so that 我可以针对真实现场进行 Fit-Gap 评审。
6. As a 实现代理, I want 一个唯一且有依赖顺序的实施规格, so that 我不会绕过领域内核直接堆叠页面。
7. As a 计划员, I want 从 ERP 接收生产订单及来源版本, so that MES 不再维护另一套计划真相。
8. As a 计划员, I want 重复的同一入站消息只产生一个业务结果, so that 网络重试不会创建重复订单。
9. As a 计划员, I want 查看订单入站的接受或拒绝原因, so that 我可以处理编码、版本或数据完整性问题。
10. As a 计划员, I want 将已接收订单下达为可执行订单, so that 车间只执行经过确认的计划。
11. As a 计划员, I want 下达时冻结完整执行快照, so that 模板后续修改不会改变已经投产产品的依据。
12. As a 计划员, I want 查看执行快照引用的产品、BOM、路线、追溯、测试和身份版本, so that 订单执行依据可以审计。
13. As a 计划员, I want 按受控状态机暂停和恢复订单, so that 暂停期间不会继续投入新产品或正常推进。
14. As a 计划员, I want 只在尚未投产时取消订单, so that 已发生的制造责任不会被取消状态抹除。
15. As a 计划员, I want 在投产后通过受控变更处理 ERP 订单变化, so that 来源变更不会静默覆盖冻结快照。
16. As a 计划员, I want 查看计划数、投产数、合格数、报废数、未投产数和在制数的平衡, so that 工单数量口径可核对。
17. As a 计划员, I want 仅在全部已投产 SN 合格完工或报废且没有未决质量保留时标记执行完成, so that 工单不会提前结束。
18. As a 计划员, I want 仅在仓储和 ERP 回执完成并通过对账后关闭订单, so that 制造完成不被误当成跨系统业务闭环。
19. As a 工艺工程师, I want 维护版本化的线性工艺路线, so that 不同产品和时期可以使用不同执行依据。
20. As a 工艺工程师, I want 对路线版本执行审批和生效控制, so that 未批准的路线不能用于订单下达。
21. As a 工艺工程师, I want 将参考路线作为可配置样板而非代码常量, so that 现场确认后可以调整站序。
22. As a 工艺工程师, I want 为返工定义批准的返工作业或返工路线, so that 异常产品不会通过任意跳站回到正常流。
23. As a 工艺工程师, I want 查看使用某个模板版本的订单和 SN, so that 变更影响能够被分析。
24. As a 工艺工程师, I want 对已发布模板创建新版本而不是原地改写, so that 历史执行依据保持不变。
25. As a 系统集成方, I want 产品编码、物料编码和计量单位以 ERP 为权威, so that MES 不制造跨系统主数据冲突。
26. As a 工艺工程师, I want MES 管理路线、工位、追溯策略、作业参数和测试规范, so that 执行规则由制造域负责。
27. As a 物料人员, I want 接收来自 ERP 或 WMS 的线边物料交接, so that MES 能记录车间责任范围内的可用物料。
28. As a 物料人员, I want 物料交接与工单发料保持为不同事务, so that 收到线边不等于已分配给某个订单。
29. As a 物料人员, I want 工单发料与实际耗用保持为不同事务, so that 计划分配不会冒充产品实际用料。
30. As a 物料人员, I want 通过只追加事务记录交接、发料、耗用、退料、冲正和调整, so that 余额变化能够追溯。
31. As a 物料人员, I want 当前线边余额和工单可用量由事务投影得出, so that 用户不能直接改写总数掩盖历史。
32. As a 物料人员, I want 默认禁止未授权负库存, so that 缺料不会被悄悄带入制造事实。
33. As a 物料人员, I want 对每次冲正引用原事务并填写原因, so that 更正责任清晰。
34. As a 物料人员, I want 查看物料事务与 ERP 回写状态, so that 制造账与企业账可以对账。
35. As a 工艺工程师, I want 按产品和物料配置 SN、Lot 或数量三种追溯粒度, so that 追溯成本与召回风险相匹配。
36. As a 操作工, I want 在 `START_WIP` 扫描或确认已经取得的成品身份, so that 产品身份与订单及执行快照正式关联。
37. As a 系统集成方, I want 成品 SN 来源和分配时间可配置, so that ERP、标签系统或 MES 受控发号均可接入。
38. As a 系统集成方, I want MAC、IMEI 和证书只来自授权系统或受控号池, so that MES 不会随机伪造受监管身份。
39. As a 质量人员, I want 产品身份分配、绑定、解绑、作废和换标都有事件记录, so that 身份历史可审计。
40. As a 操作工, I want 标签打印、补打和作废与身份本身分开记录, so that 标签载体不会被误当成产品身份。
41. As a 操作工, I want 未下达、已暂停、已完成或已关闭订单拒绝新的 `START_WIP`, so that 投产遵守订单状态。
42. As a 操作工, I want 系统校验计划数量和允许的超投规则, so that 投产不会无意超出订单边界。
43. As a 操作工, I want 扫描 SN 后看到当前应执行工序和所需数据, so that 我能减少错站和漏采集。
44. As a 操作工, I want 在不匹配的工位或错误顺序过站时收到明确拒绝, so that 跳站不会污染谱系。
45. As a 操作工, I want 每次过站记录工厂、产线、工位、工序、人员、时间和结果, so that 制造履历可还原。
46. As a 操作工, I want 正常过站同时更新当前状态并追加制造事件, so that 查询效率和历史可信度可以兼得。
47. As a 操作工, I want 命令失败时不产生部分状态或孤立事件, so that 一次操作保持原子性。
48. As a 产线主管, I want 查看每个订单和工序的在制 SN, so that 我可以识别阻塞和异常积压。
49. As a 产线主管, I want 暂停订单后禁止新投产和正常推进, so that 现场能够真正执行停线决策。
50. As a 操作工, I want 在装配工序绑定关键部件 SN, so that 成品可以反查关键部件。
51. As a 操作工, I want 对批次件记录 Lot 和实际数量, so that 批次召回能够定位受影响成品。
52. As a 操作工, I want 对数量件按批准规则记录实际耗用或回冲, so that 低价值辅料不被强制逐件采集。
53. As a 操作工, I want 同一关键部件 SN 不能同时绑定多个有效成品, so that 部件身份关系唯一可信。
54. As a 操作工, I want 解绑或替换关键部件时保留原绑定和更正原因, so that 返修历史不会消失。
55. As a 质量人员, I want 从关键部件 SN 或 Lot 反查所有受影响成品, so that 供应商异常和召回分析可执行。
56. As a 操作工, I want 在固件配置工序记录固件、配置包、校验值、工具和执行结果, so that 软件配置成为谱系的一部分。
57. As a 工艺工程师, I want 固件和配置要求来自订单执行快照, so that 已投产产品不会随默认版本变化。
58. As a 操作工, I want 固件配置失败形成不可覆盖的执行记录, so that 重试成功不会抹掉原失败。
59. As a 质量工程师, I want 维护版本化测试规范及其必测项、类型、单位和判定规则, so that 测试结果有明确依据。
60. As a 质量工程师, I want 测试规范经过审批后才能用于订单下达, so that 未批准阈值不会进入生产。
61. As a 测试操作员, I want 每次测试形成独立执行记录和逐项测量, so that 结果不仅是一个总 Pass 或 Fail。
62. As a 测试操作员, I want 记录设备、夹具、操作主体、起止时间和原始报告引用, so that 测试证据可以复核。
63. As a 测试操作员, I want 系统根据冻结规范判定必测项和上下限, so that 前端硬编码不会成为质量标准。
64. As a 质量工程师, I want 复测创建新执行并关联原失败, so that 完整失败、返工和复测链条被保留。
65. As a 质量工程师, I want 原始测试执行和测量在确认后不可编辑, so that 质量证据不会被结果覆盖。
66. As a 操作工, I want 测试或检验失败创建独立不合格记录, so that 失败事实与后续管理处置分离。
67. As a 质量工程师, I want 不合格记录包含对象、发现工序、缺陷、关联测试和证据, so that 问题可以被分类和调查。
68. As a 质量工程师, I want 不合格触发独立质量保留, so that 产品在处置前无法正常流转或完工。
69. As a 质量工程师, I want 对不合格作出返工、报废或让步接收的正式处置, so that 每个决定都有授权主体和依据。
70. As a 质量工程师, I want 返工处置引用批准的返工作业并指定复测要求, so that 返工闭环可验证。
71. As a 质量工程师, I want 让步接收必须引用有效审批依据, so that 例外放行不会成为任意操作。
72. As a 质量工程师, I want 报废成为该 SN 的终态并进入订单数量平衡, so that 报废品不会重新进入正常流。
73. As a 质量工程师, I want 只有满足处置和复测条件后才能解除质量保留, so that 放行不只是填写自由文本。
74. As a 操作工, I want 无权批准处置或解除质量保留, so that 执行与质量决策职责分离。
75. As a 系统管理员, I want 技术管理权限不自动包含业务处置权限, so that 管理账号不能绕过业务审批。
76. As a 质量工程师, I want 查看待处理不合格、质量保留、处置和返工队列, so that 异常工作可以持续管理。
77. As a 操作工, I want 只有路线要求、物料、固件、必测项、终检和质量门禁全部满足后才能 `COMPLETE`, so that 合格完工代表完整制造事实。
78. As a 系统, I want 制造完工、仓储接收和 ERP 入账保持三个可关联状态, so that 不同责任边界不会被一个状态混淆。
79. As a 仓储交接员, I want 接收或拒绝完工成品交接并记录回执, so that 成品责任转移可追踪。
80. As a 计划员, I want 仓储或 ERP 暂未回执时仍能看到制造已完成但订单未关闭, so that 跨系统延迟不篡改制造事实。
81. As a 系统集成方, I want MES 领域变更和出站消息在同一数据库事务中提交, so that 不会出现已完工但没有待发送消息。
82. As a 系统集成方, I want 出站消息具备 Pending、Processing、Sent、Failed 和 DeadLetter 状态, so that 投递过程可运营。
83. As a 系统集成方, I want 失败投递记录每次尝试、错误和下一次重试时间, so that 问题能够诊断。
84. As a 系统集成方, I want 并发发送器只能认领一次待处理消息, so that 多实例运行不会产生重复发送竞争。
85. As a 系统集成方, I want 接收 ERP 回执并按业务幂等键关联原消息, so that 发送成功和对方入账成功可以区分。
86. As a 系统集成方, I want 对失败和死信消息执行受权人工重试或补偿, so that 临时故障无需直接改数据库。
87. As a 系统集成方, I want ERP 模拟器调用与真实适配器相同的契约, so that 演示不会绕过正式集成边界。
88. As a 计划员, I want 查看订单、完工、耗用、报废和回执的对账差异, so that 订单关闭有可解释依据。
89. As a 质量人员, I want 按成品 SN 查询从订单快照到仓储和 ERP 状态的完整谱系, so that 客诉和召回可以基于事实调查。

91. As a 质量人员, I want 谱系导出包含版本、生成时间和完整性校验值, so that 证据包可以复核是否被更改。
92. As a 质量人员, I want 对缺失的上游 PCBA 历史只保存外部引用, so that 系统不会补造不存在的厂内制造事件。
93. As a 审计人员, I want 制造事件与业务审计分开保存并可关联, so that 制造事实和管理操作各自语义清晰。
94. As a 审计人员, I want 关键命令记录主体、角色、时间、关联 ID 和结果, so that 权限与责任可追踪。
95. As a 安全管理员, I want 账号可以组合业务角色但关键能力逐项授权, so that 小型工厂兼岗不破坏职责分离。
96. As a 安全管理员, I want 操作工、产线主管、质量工程师、计划员、物料交接员、工艺工程师和系统管理员权限可验证, so that UI 隐藏不是唯一防线。

100. As a 运维人员, I want 数据库结构通过显式 Migration 安装和升级, so that API 启动不会自动建库、删库或猜测结构。
101. As a 运维人员, I want 在空库和带历史数据的上一版本数据库上验证升级, so that 发布同时证明新装和升级路径。
102. As a 运维人员, I want 每日完整备份、升级前备份和实际恢复演练, so that RPO 与 RTO 假设有技术证据支持。
103. As a 运维人员, I want 失败 Migration 阻止应用发布且不自动重建数据库, so that 数据不会为追求启动成功而被破坏。
104. As a 计划员, I want 管理端提供订单、在制、物料、集成和对账核心工作台, so that 日常工作不依赖直接调用 API。
105. As a 操作工, I want 工位端以扫码和当前任务为中心并提供明确防错提示, so that 高频操作不被管理菜单干扰。
106. As a 质量工程师, I want 质量端支持不合格、保留、处置、返工和复测闭环, so that 关键质量动作不需要数据库操作。
107. As a 客诉调查人员, I want 追溯端可以按 SN、关键件 SN 或 Lot 查询和导出, so that 正查与反查都能完成。
108. As a 用户, I want 所有关键拒绝都返回可理解且可行动的中文业务错误, so that 我知道失败原因和下一步责任人。
109. As a 用户, I want 重复提交同一业务命令不会产生重复事实, so that 扫码抖动和网络重试不会污染数据。
110. As a 测试人员, I want 使用固定且相互隔离的正常、返工、报废和集成异常数据集, so that 证据可以重复生成和比较。
111. As a 测试人员, I want 在真实 SQL Server 上验证 Migration、约束、事务、幂等和并发, so that SQLite 通过不会冒充部署能力。
112. As a 测试人员, I want 通过真实浏览器执行计划、工位、质量和追溯工作流, so that API 正确之外也证明用户路径可用。
113. As a 项目经理, I want 每条 Must 需求至少关联一个自动测试或人工验收步骤, so that 完成状态有证据而不是口头判断。
114. As a 项目经理, I want 每个版本生成包含构建、测试、截图、谱系、Migration、部署和限制的证据包, so that 陌生人可以复现技术结论。
115. As a 项目经理, I want Critical 和损害制造事实的 Major 缺陷阻止发布, so that 时间压力不会降低追溯可信度。
116. As a 项目经理, I want 将未验证、已实现、技术验证通过、制造从业者评审通过和真实现场验证通过分级, so that 项目陈述不会越过证据等级。
117. As a 客户关键用户, I want 在真实 SOP、样品、设备、接口和账号准备后执行 UAT, so that 业务可用性由实际用户而非开发人员代签。

## Implementation Decisions

- **项目定位与证据边界：** 系统名称和对外陈述统一使用“单厂工业路由器整机装配 MES 试点候选系统”。没有制造从业者评审和现场证据时，最高可信度为“技术验证通过”。自动化测试不能升级业务真实性等级。
- **救援方式：** 保留现有 .NET、Vue、SQL Server、认证、容器化和可复用测试骨架，按领域边界增量重构。现有测试只证明旧行为；只有与本规格一致并经过新验收链路覆盖后，才成为新基线证据。
- **实施顺序：** R0 固定规格、需求追踪和旧行为；R1 建立 Migration、真实 SQL Server 与安全配置门禁；R2 建立订单、快照、身份、WIP 和物料事务；R3 建立固件、测试、质量、完工与谱系；R4 建立 Inbox、Outbox、回执和对账；R5 建立核心角色工作台及浏览器链路；R6 建立部署、恢复和版本证据包。后续阶段不得绕过前置阶段的退出门禁。
- **系统边界：** ERP 负责产品和物料编码、计量单位、生产订单和计划数量；BOM 来源由实施现场在 ERP 或 PLM 之间确认。MES 负责执行快照、工艺路线、工位、追溯策略、作业参数、测试规范和全部制造执行事实。
- **试点边界：** 制造范围从已完成上游测试的 PCBA 和其他来料进入整机装配开始，到合格制造完工和仓储交接为止。外部供应商或上游工厂历史只能作为有来源的外部引用，不能生成虚假的本厂事件。
- **领域架构：** 采用模块化单体。按主数据与执行依据、生产订单、产品身份与标签、制造执行、物料事务、固件与测试、质量、完成与仓储、集成、身份权限、审计与证据划分清晰模块。模块间通过应用命令、查询和领域标识协作，禁止页面直接拼接数据库写入。
- **状态与历史：** 关系表保存当前可查询状态，只追加事件保存已确认制造事实。领域命令在一个数据库事务内完成规则验证、当前状态变更、事件追加、业务审计和必要 Outbox 写入。事件更正通过引用原事件的冲正或补偿事实表达。
- **生产订单状态机：** 使用 `已接收 -> 已下达 -> 生产中 <-> 已暂停 -> 执行完成 -> 已关闭`。仅未投产订单可取消。暂停禁止新投产与正常推进；执行完成要求所有已投产 SN 合格完工或报废且无未决质量保留；关闭还要求仓储/ERP 回执与对账完成。
- **执行快照：** 订单下达时创建自包含、不可原地改写的执行快照，至少包含产品版本、单层 BOM、路线版本及工序、追溯粒度、身份来源策略、固件/配置要求、测试规范和完成门禁。模板变更不影响已下达订单。
- **订单变更：** ERP 在订单下达后的变更不能覆盖原快照。系统记录来源版本和差异，按配置拒绝、要求人工审批或生成新的受控执行版本；已经发生的制造事实永不重写。
- **路线模型：** 第一期只实现版本化线性路线、合格前进、指定工序返工和报废终止，不实现通用图形化路由引擎。参考路线用于技术验证，但必须保持可配置并标记为待现场确认。
- **产品身份：** 成品 SN 来源、分配时机和授权系统可配置。`START_WIP` 只负责将已经取得的身份与订单、产品和执行快照关联。MAC、IMEI、证书等受控身份由授权适配器或号池提供。
- **标签模型：** 打印、补打、作废、换标与身份分配分开建模。标签事件记录模板版本、执行主体、时间和关联身份；补打和换标不覆盖原记录。
- **制造事件：** 至少覆盖投产、过站、物料绑定/解绑、批次或数量耗用、固件配置、测试执行、检验、不合格、质量保留、处置、返工、复测、报废、制造完工和交接。事件具有稳定 ID、发生时间、记录时间、主体、位置、业务对象和关联因果 ID。
- **物料事务：** 交接、工单发料、实际耗用、退料、冲正和调整是不同事务类型。线边余额与工单可用量由事务汇总；禁止直接改写余额。每个事务具备业务幂等键、计量单位、来源和可选原事务引用。
- **追溯粒度：** 成品按 SN；关键部件按 SN；批次件按 Lot 与数量；数量件按批准规则逐 SN 记录或回冲。粒度属于版本化产品/物料执行策略，不把所有物料强制成同一种方式。
- **部件绑定：** 有效关键部件 SN 默认只能属于一个有效成品关系。解绑、替换和纠错追加关系事件并保留原因。正向谱系和按关键件或 Lot 的反向影响查询使用同一事实来源。
- **固件与配置：** 执行记录保存要求版本、实际版本、配置包、校验值、工具/设备、主体、时间和结果。具体固件值及设备参数属于产品和现场数据，不写死为行业常量。
- **测试规范：** 测试定义和测试执行分离。批准的版本化规范定义项目、数据类型、单位、必测条件和判定规则；订单快照冻结所用版本。具体端口、阈值和设备参数保持为待产品规范确认内容。
- **测试执行：** 每次执行和每项测量均为只追加记录，包含设备、夹具、主体、时间、总体结果和原始报告引用。复测产生新记录并引用原失败，不允许把失败改成通过。
- **质量模型：** 不合格、质量保留和处置决定分别建模。失败可创建不合格并触发保留；保留阻止正常推进和完工；质量角色选择返工、报废或有依据的让步接收；解除保留必须满足处置与复测条件。
- **返工与报废：** 返工引用批准作业或路线版本并明确复测要求。报废为 SN 终态，进入订单数量和集成回写；相关物料按批准规则保留责任或产生冲正事务，不能通过删除原耗用解决。
- **完成边界：** 制造合格完工、仓储接收和 ERP 入账是三个状态。`COMPLETE` 校验路线、物料、固件、必测项、终检和质量门禁；仓储交接记录责任转移；ERP 回执记录企业账处理。订单关闭依赖三者的对账结果。
- **谱系查询：** 按成品 SN 返回订单和冻结快照、身份和标签历史、制造事件、部件关系、Lot/数量耗用、固件、测试及测量、质量处置、返工复测、完工、仓储与 ERP 状态。导出包含版本、生成时间和完整性校验值。
- **入站集成：** 所有 ERP/WMS 入站先进入幂等 Inbox，保存来源、消息 ID、业务键、契约版本、载荷校验信息、处理结果和错误。重复消息返回原处理结果，不再次执行领域命令。
- **出站集成：** 领域状态与 Outbox 同事务提交。发送器使用至少一次投递和幂等消费假设，管理 `Pending / Processing / Sent / Failed / DeadLetter`、租约/认领、尝试历史、退避、人工重试和回执；不宣称严格 exactly-once。
- **接口契约：** 候选接口包括产品、物料和生产订单入站，物料交接入站，完工、耗用/冲正、报废和仓储交接出站。所有契约版本化并明确业务幂等键、必填字段、接受/拒绝结果、错误码和回执。真实 ERP 字段在获得目标版本文档和样例报文前不承诺。
- **模拟适配器：** ERP 模拟器只模拟外部系统行为，必须通过相同正式契约、Inbox、Outbox 和回执路径工作，禁止直接写入 MES 业务表。
- **授权模型：** 账号可组合计划员、工艺工程师、操作工、产线主管、质量工程师、物料交接员、系统管理员和运营负责人等业务角色。服务端按具体能力授权；主角色只影响默认工作台。操作工不能质量处置，产线主管不能替代质量审批，系统管理员不自动拥有业务审批权。
- **审计模型：** 业务审计记录登录、安全管理、主数据批准、订单状态变更、质量处置、人工重试和配置变更。制造事件与业务审计分开存储，但通过关联 ID 连接；两者均不允许普通业务接口删除。
- **数据库演进：** EF Core Migration 是唯一结构演进机制。废除 API 启动时的 `EnsureCreated`、结构猜测、自动删库和重建。部署显式执行 Migration，API 启动只做兼容性和依赖就绪校验。
- **旧数据策略：** 旧数据保留为 Legacy 只读或经过可证明的字段迁移。无法从原记录证明的快照、Lot、固件、测量和处置不得补造；新模型上线后的新订单必须完整使用新领域契约。
- **SQL Server 约束：** 唯一性、外键、并发令牌、事务隔离、精度、时间语义和索引以 SQL Server 为准。SQLite 仅用于可选快速反馈，不能作为发布门禁的数据库证据。
- **应用接口：** 写操作使用表达业务意图的命令而非通用实体更新；响应提供稳定错误码、中文可行动说明、关联 ID 和幂等结果。查询面向工作台和谱系读取模型，不把数据库实体直接暴露为公共契约。
- **工作台：** R5 只交付计划/订单、工位执行、质量异常、物料与集成对账、谱系查询这些支撑四条验收场景的页面。经营总览只能使用已经可靠产生的执行事实，不以装饰性指标代表领域完成。
- **工位体验：** 工位端保持高频扫码、稳定布局、当前 SN、下一工序、所需采集、防跳站和明确错误提示。管理功能不挤入工位主流程；关键防错由服务端强制而非只依靠界面。
- **生产配置门禁：** 正式环境使用 HTTPS、外置密钥、最小权限数据库账号、受限 CORS、非演示初始化和内部网络隔离。检测到示例密钥、演示账号策略、Development 环境或高权限数据库配置时拒绝进入生产就绪状态。
- **运行可观测性：** 提供不泄密的存活和就绪检查、结构化日志、关联 ID、集成队列状态、失败原因和关键业务指标。日志不替代制造事件或业务审计。
- **备份恢复：** 试点候选暂以 RPO 24 小时、RTO 4 小时作为待现场确认目标。每日完整备份、升级前备份、恢复到隔离环境及恢复后冒烟均需自动或可重复执行并留证。
- **完成定义：** 一个能力只有在实现、适当层级测试、唯一高层验收接缝覆盖、需求追踪和证据包更新后才可标记为“技术验证通过”。代码存在、页面可见或旧测试通过只能标记为“已实现”或更低。

## Testing Decisions

- **好测试的定义：** 测试只观察公共 API、浏览器工作流、持久化后可查询业务结果、正式消息契约和部署行为，不断言私有方法、内部类形状、组件树或临时表结构。测试重点是不变量、授权拒绝、事务原子性、历史不可覆盖、幂等结果和用户可完成的业务目标。
- **唯一最高验收接缝：** 通过真实浏览器与公共 API，在真实 SQL Server 上，以固定成品 SN 跑通“订单入站 -> 下达并冻结执行快照 -> 物料交接/发料 -> START_WIP -> 关键件与批次耗用 -> 固件配置 -> 测试与质量 -> 制造完工 -> 仓储交接 -> Outbox 回写及 ERP 回执 -> 对账与订单关闭 -> 完整谱系查询和导出”。这是唯一发布级业务验收口径。
- **场景一，正常完工：** 验证重复订单入站幂等、快照冻结、三种物料粒度、固件和逐项测试通过、终检、完工、仓储接收、ERP 回执、订单关闭和固定 SN 完整谱系。模板在订单下达后修改不得影响该 SN。
- **场景二，失败返工复测：** 验证测试失败、原测量保留、不合格、质量保留、操作工无处置权限、质量返工决定、批准返工作业、复测新记录、解除保留和最终完工。保留未解除时必须拒绝后续完工。
- **场景三，报废与数量平衡：** 验证严重不合格、质量报废、物料责任/冲正、有在制订单取消被拒绝、订单计划/投产/合格/报废/未投产平衡，以及报废和对账完成后的受控执行完成或短结。
- **场景四，集成失败恢复：** 验证 Inbox 重复与载荷冲突、Outbox 与领域事务原子性、模拟 ERP 暂时失败、失败记录、自动/人工重试、并发认领、对方幂等接收、回执和对账前禁止关单。
- **固定测试数据：** 四个场景使用稳定且互不复用的订单号、成品 SN、关键件 SN、Lot、消息 ID 和测试运行 ID。数据明确标记为非生产；重复运行通过隔离数据库或受控重建实现，不依赖随机值掩盖幂等问题。
- **SQL Server 门禁：** 发布流水线必须在临时真实 SQL Server 上验证空库 Migration、上一发布版本带数据升级、失败回滚、约束、唯一键、精度、事务、并发、Inbox 幂等和 Outbox 认领。SQLite 测试可以保留为快速反馈，但结果不计入 SQL Server 门禁。
- **API/应用测试：** 覆盖每个领域命令的成功、非法状态、重复提交、角色拒绝和事务回滚；验证错误码和中文操作建议。优先扩展现有 Web 应用测试宿主和 SeamTests 的公共 HTTP 风格，不新增第二套应用调用方式。
- **领域单元测试：** 仅用于高密度验证订单状态机、完成门禁、质量处置、物料余额、路线推进和数量平衡等纯业务不变量。单元测试不能替代 API、SQL Server 或浏览器证据。
- **契约测试：** 对每个 ERP/WMS 候选接口验证版本、必填字段、枚举、业务幂等键、重复响应、错误分类和回执关联。模拟器与真实适配器共享这些契约测试。
- **浏览器测试：** 使用真实前端、API 和 SQL Server 完成计划员下达、物料交接、操作工执行、质量处置、集成重试和谱系导出。断言用户可见状态、可执行命令和权限边界，不锁定 DOM 实现细节。
- **关键负向测试：** 至少覆盖未下达投产、暂停后投产/过站、跳站、超投、未发料耗用、未授权负库存、关键件重复绑定、必测项缺失、测量越界、未决保留完工、操作工处置、系统管理员业务越权、重复 Inbox、并发 Outbox、对账前关单和升级失败自动重建等拒绝路径。
- **迁移兼容测试：** 使用脱敏的上一版本结构和可证明数据作为升级夹具。对无法证明的新事实保持空缺或 Legacy 标记，验证升级不会编造制造历史。
- **部署与恢复测试：** 验证 Compose 私有化启动、HTTPS、内部端口隔离、生产配置门禁、存活/就绪、Migration、冒烟、备份、隔离恢复和恢复后固定 SN 查询。恢复时间只记录实测值，不以配置文件宣称 RTO 已达标。
- **安全测试：** 验证所有角色的允许和拒绝矩阵、禁用账号、令牌边界、敏感配置不进入响应/日志、CORS、HTTPS 和最小权限数据库连接。隐藏按钮不构成授权证据。
- **性能与容量：** 当前没有真实班次、工位并发、峰值扫码和报告大小数据，不设置虚构生产 SLA。先提供可重复基准框架，待现场容量确认后制定响应时间、吞吐和保留期门禁。
- **需求追踪：** 每条 Must 需求关联至少一个测试或人工验收步骤；测试结果记录版本、提交、环境、数据库版本、输入身份和证据位置。没有覆盖的需求必须说明原因和风险接受人。
- **证据包：** 每个候选发布包含需求追踪矩阵、各层测试结果、四条高层场景、关键浏览器截图、固定 SN 谱系导出及校验值、SQL Server 新装/升级、权限拒绝、部署恢复结果、已知限制和未验证假设。
- **现有测试先例：** 现有认证、主数据、工单、过站、质量、完成和第一期端到端 SeamTests 可作为公共 HTTP 测试结构的先例；其中 SQLite、旧站序、简化放行和直接完工语义必须按本规格重写或降级为 Legacy 行为记录。
- **发布退出标准：** Must 需求完成并有追踪；四条场景及关键负向测试通过；真实 SQL Server、浏览器、权限、部署和恢复门禁通过；Critical 为零，损害制造事实或追溯的 Major 为零；证据包可由未参与开发的人按说明复现。

## Out of Scope

- 上游 SMT、锡膏、贴片、回流焊、AOI、ICT 和 PCBA 厂内制造过程。
- 完整 WMS，包括库位、上架、波次、拣货、盘点、立库和仓内优化；本期只管理 MES 责任范围内的线边交接、发料、耗用和成品交接。
- APS、高级排程、有限产能优化、甘特图和跨工厂供应链计划。
- PLC、SCADA、设备实时闭环控制、完整设备管理、预测性维护和边缘离线执行。
- 完整 QMS、SPC、实验室管理、供应商质量、8D/CAPA 和通用 MRB 平台；仅实现本试点闭环所需质量能力。
- OEE、精确工时、节拍损失和经营驾驶舱，直到可靠的设备、停机、班次和工时数据来源被现场确认。
- 多工厂、多租户 SaaS、跨法人结算、全球组织模型和复杂数据域隔离。
- 通用 BPM/审批流平台、低代码表单平台或可编程图形化工艺引擎。
- 多层递归 BOM、替代料优化、MRP 运算和采购补货。
- 企业 SSO、高可用集群、异地灾备、零停机升级和生产级云原生编排；这些能力需由真实基础设施需求驱动。
- 对特定用友、金蝶、SAP 或其他 ERP 产品版本的正式联调实现，直到获得接口文档、样例报文、技术账号和沙箱。
- 真实标签打印机、测试设备、夹具、MAC/证书号池和文件存储集成；本期先定义适配边界和经过契约测试的模拟器。
- 真实客户数据迁移、现场安装、用户培训、试运行和最终验收。
- 声称系统已商业化、已上线、已通过客户验收、已被真实工厂验证或满足未执行的法规认证。
- 为补齐演示而伪造上游生产历史、测试阈值、设备参数、ERP 字段、客户 SOP、审批规则或性能数据。

- 本规格整合现有项目章程、业务需求、解决方案、实施治理、测试验收、证据计划和 ADR 决策，替代此前以二期 UI/工作台扩展为中心的实施优先级。旧二期规格保持暂停，仅可作为已有界面需求参考。
