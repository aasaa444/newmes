# 不合格记录与质量保留

Ticket 11 在测试失败和现场异常之上建立质量隔离闭环的前半段：不合格记录保存“发现了什么”，质量保留保存“为什么暂停正常制造流转”。返工、报废、让步接收和解除保留属于 Ticket 12，不能通过本 Ticket 的自由文本或数据库更新提前实现。

## 领域边界

一次已确认的测试失败或操作工现场报告形成一条新的 `NonconformanceRecord`。记录包含产品身份、订单和执行快照、发现工序、缺陷代码、现象、证据引用、发现时间、位置、报告人、来源业务键和制造事件。测试失败还引用原 `TestRun`，因此质量人员可以沿因果链回到原始测量与测试台报告。

`QualityHold` 是独立的产品隔离事实。第一条未决不合格为产品建立有效保留；同一产品后续发现的其他不合格仍各自保存，但关联已有保留，不重复增加订单的保留产品数量。数据库过滤唯一索引保证每台产品任一时刻最多一个 `Active` 保留。

这种拆分避免三个常见错误：把失败测试结果当成产品处置、每个缺陷重复隔离同一台产品，以及仅修改一个布尔字段后无法说明谁在何时基于什么证据执行了隔离。

## 触发与制造门禁

系统当前支持两个触发来源：

- 测试服务端判定一次运行失败时，在原测试事务内自动追加不合格和质量保留。
- 操作工通过 `POST /api/quality/nonconformances` 报告当前工序观察到的异常；命令不能包含处置或放行决定。

有效保留在任何新业务事实写入前阻止正常装配投料、固件配置、测试或复测，并使订单的 `complete-execution` 返回 `PRODUCTION_ORDER_QUALITY_HOLD_OPEN`。同一命令已经成功提交后的幂等回放仍可读取原结果，但保留开始后不能以新幂等键绕过门禁。

被拒绝的正常过站不创建物料事务、固件执行、测试运行或制造事件。权限拒绝和业务拒绝仍按系统审计策略保存为拒绝证据，这不属于制造部分事实。

## 权限与工作台

操作工拥有 `DefectReport`，只能报告现场异常，不能读取跨产品质量队列、决定处置或解除保留。质量工程师拥有 `QualityQueueRead`，可通过 `GET /api/quality/nonconformances` 查看不合格、SN、订单、工序、测试引用、证据和保留条件，但不能代替操作工提交现场报告。

该职责分离表达的是当前组织基线。真实项目可以通过受控角色组合适配岗位兼任，但不能只隐藏页面按钮；服务端能力检查和拒绝审计必须同时成立。

## 幂等、事务与不可变证据

人工报告以规范化后的 `SourceSystem + IdempotencyKey` 为业务键，并以全部业务字段计算 `SHA-256-JSON-V1` 哈希。完全相同的重投返回原不合格并标记 `IsReplay`；同键不同载荷返回 `NONCONFORMANCE_IDEMPOTENCY_CONFLICT`，不覆盖首次事实。

一次新报告中的不合格、可能的新保留、订单保留计数、制造事件和成功业务审计在同一个 SQL Server `Serializable` 事务中保存。自动测试失败还把测试运行、逐项测量与上述质量事实纳入同一事务。数据库故障会整体回滚。

制造事件的因果关系为：测试失败事件（若有） -> `NONCONFORMANCE_RECORDED` -> 首次 `QUALITY_HOLD_STARTED`。实体外键与相同关联 ID 支持从工作台证据追溯到制造时间线和业务审计。Ticket 11 的不合格和保留表由 SQL Server 触发器拒绝普通更新与删除；后续处置必须追加受控事实，而不是改写历史。

## 现场落地边界

当前证据证明 HTTP 契约、角色边界、事务、SQL Server 约束和制造门禁可执行，但不代表已经完成真实工厂验证。试点前仍需由客户确认缺陷代码字典、工序与报告岗位、照片或报告存储、证据保留期限、设备自动报错映射、隔离区实物流转、通知升级时限、质量处置权限和电子签名要求。未经确认的内容应进入 Fit-Gap 或 RAID，不在代码中编造默认业务规则。
