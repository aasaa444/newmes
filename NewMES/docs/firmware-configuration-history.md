# 固件与配置执行履历

Ticket 09 把订单冻结的固件要求转化为逐台成品、逐次尝试的执行证据。系统不把某个工业路由器固件版本写成行业常量；要求版本、配置包、校验算法和期望校验值都来自已批准模板，并在订单下达时进入不可改写的执行快照。

## 冻结要求

每项固件要求包含要求编码、执行工序、要求版本、配置包、校验算法、期望校验值、批准依据和是否必需。新模板发布时这些字段必须完整且工序必须存在于路线中。旧快照缺失证据时返回 `FIRMWARE_SNAPSHOT_REQUIREMENT_INVALID`，不会用代码默认值补造制造依据。

## 执行尝试

每次尝试分别保存要求与实际校验算法、实际版本、实际配置包、实际校验值、工具/设备标识及版本、操作主体、位置、开始/结束/记录时间、结果与关联 ID。设备上报诊断与 MES 判定诊断分开保留，避免证据不匹配时覆盖设备原始故障信息。服务端同时比较要求版本、配置包、校验算法和校验值；操作端即使报告成功，只要任一证据不匹配，落库结果仍为 `Failed`，MES 判定代码为 `FIRMWARE_EVIDENCE_MISMATCH`，且不会推进路线。

失败记录不可更新或删除。下一次尝试必须以 `RetryOfExecutionId` 引用该要求的最新失败；重试生成新执行记录和新制造事件，不覆盖原失败。相同 `SourceSystem + IdempotencyKey` 的完全重投返回原结果，不同载荷返回稳定冲突。

只有当前订单为 `InProduction`、成品当前工序等于冻结要求工序，并且该工序的所有必需固件要求都已有唯一成功执行时，系统才追加 `FIRMWARE_CONFIGURATION_COMPLETED` 并推进到冻结路线下一工序。其他工序的固件要求在到达各自冻结工序后独立执行，不会阻塞当前工序。验证、执行记录、制造事件、路线状态和业务审计在同一 SQL Server 事务中提交。

## API 与权限

- `POST /api/execution/firmware/{finishedSerialNumber}/executions`
- `GET /api/execution/firmware/{finishedSerialNumber}`
- `GET /api/genealogy/products/{finishedSerialNumber}/firmware`

执行和工位查询需要 `StationExecute`；固件谱系查询需要 `GenealogyRead`。质量人员可以查看全部失败和重试历史，但不能执行固件写入。执行与谱系响应公开主体、位置、工序、时间、生产订单/快照/制造事件以及关联 ID；业务拒绝返回稳定错误码、中文行动说明和关联 ID。

当前实现记录工位或适配器提交的执行证据，不直接控制烧录设备。具体设备协议、签名验证、密钥托管和安全启动证明必须在取得目标产品与设备接口资料后，通过受控适配器扩展，不能由本试点虚构。
